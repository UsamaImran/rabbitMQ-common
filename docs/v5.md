# rabbitmq-common v6

A TypeScript-first RabbitMQ utility for Node.js built on `amqplib`, focused on clean producer/consumer APIs, topology management, dead-letter queues, backpressure, and recovery.

## v6 reliability changes

- DLQ configuration is set when creating a `Producer` or `Consumer`; it is **not** a `consume()` option.
- Queue and exchange assertion caches are scoped to the AMQP channel.
- Queue topology signatures include relevant configuration.
- Batch publishing treats `false` from `sendToQueue()` / `publish()` as backpressure and never republishes the same message.
- Drain waits reject when the channel closes or errors.
- Consumer recovery is single-flight and restores runtime bindings.
- Recovery uses exponential backoff with optional jitter.
- Permanent topology errors such as `406 PRECONDITION_FAILED` are not blindly retried.
- Obsolete duplicate `producer1.ts` / `consumer1.ts` implementations were removed.

See [`docs/v6.md`](./v6.md) for the migration guide.

## Installation

```bash
npm install rabbitmq-common
```

## Producer

```ts
import { Producer } from "rabbitmq-common";

const producer = new Producer("amqp://localhost", {
  useDLQ: true,
  queueOptions: {
    durable: true,
  },
});

await producer.publish("orders", {
  id: 1,
  item: "book",
});
```

The `useDLQ` setting is instance topology configuration. The first use of `orders` declares:

```text
orders_dlx
orders_failed
orders_failed --dead-letter--> orders_dlx
orders --dead-letter-exchange=orders_dlx--> ...
```

If `orders` already exists without the requested DLX arguments, RabbitMQ rejects the declaration with `406 PRECONDITION_FAILED`. The library surfaces that error; it does not try to mutate an existing queue.

### Batch publishing

```ts
const result = await producer.publishBatch("orders", [
  { id: 1 },
  { id: 2 },
  { id: 3 },
]);

console.log(result.successful, result.failed);
```

When a publish call returns `false`, the message has already entered the channel write buffer. The batch waits for `drain` and continues with the next message. It does **not** send the same message again.

### Exchange publishing

```ts
await producer.publishToExchange("events", "topic", {
  event: "order.created",
}, {
  routingKey: "orders.created",
});
```

Supported exchange types are `fanout`, `topic`, and `direct`.

## Consumer

```ts
import { Consumer, type ConsumeMessage } from "rabbitmq-common";

class OrderConsumer extends Consumer<{ id: number }> {
  async onMessage(data: { id: number }, msg: ConsumeMessage) {
    console.log(data);
  }
}

const consumer = new OrderConsumer("amqp://localhost", {
  useDLQ: true,
  maxRecoverRetries: 10,
});

await consumer.consume("orders");
```

### Exchange-bound consumer

```ts
await consumer.consume("orders", {
  exchange: "events",
  exchangeType: "topic",
  routingKey: "orders.#",
});
```

`consume()` controls consumption details such as `prefetch` and exchange binding. DLQ behavior belongs to the consumer instance:

```ts
// Correct
const consumer = new OrderConsumer("amqp://localhost", { useDLQ: true });
await consumer.consume("orders");

// v5 API — removed in v6
// await consumer.consume("orders", { useDLQ: true });
```

## Error behavior

- Successful `onMessage()` -> `ack`.
- Processing failure with DLQ enabled -> `nack(msg, false, false)`.
- Processing failure with DLQ disabled -> `nack(msg, false, true)`.
- Malformed JSON -> never requeued.
- Topology declaration failures are surfaced rather than endlessly retried.
- Channel/connection loss can trigger consumer recovery.

## Recovery

Consumer recovery is single-flight: simultaneous `error` and `close` events cannot start competing recovery loops. Recovery creates a replacement channel, reconstructs queue topology, restores tracked bindings, and recreates the consumer.

Runtime bindings are retained as desired topology:

```ts
await consumer.bindQueue("orders", "events", "payments.#");
```

After a channel replacement, that binding is restored automatically.

Recovery options:

```ts
const consumer = new OrderConsumer("amqp://localhost", {
  maxRecoverRetries: 10,
  backoffBase: 1000,
  maxBackoff: 30000,
  recoveryJitter: 0.2,
});
```

## Important RabbitMQ topology rule

RabbitMQ requires queue and exchange declarations to be equivalent to an existing resource. Changing queue arguments such as dead-letter exchange configuration is not a runtime mutation. An incompatible redeclaration causes a channel-level `406 PRECONDITION_FAILED` error.

Therefore, configure topology before the queue is first created, or migrate/recreate an existing queue before changing its topology.

## API overview

### `Producer`

- `publish(queue, message, publishOptions?, queueOptions?)`
- `publishBatch(queue, messages, publishOptions?, queueOptions?)`
- `publishToExchange(exchange, type, message, options?)`
- `publishBatchToExchange(exchange, type, messages, options?)`
- `waitForDrain()`
- `resetQueueCache(queue?)`
- `resetExchangeCache(exchange?, type?)`
- `close()`
- `isConnected()`
- `isChannelReady()`

### `Consumer<T>`

- `consume(queue, options?)`
- `bindQueue(queue, exchange, exchangeType, routingKey?)`
- `unbindQueue(queue, exchange, routingKey?)`
- `forceRecover()`
- `isActive()`
- `getCurrentQueue()`
- `getActiveBindings()`
- `close()`

### Constructor options

```ts
interface BaseRabbitOptions {
  maxRetries?: number;
  logger?: Logger;
  useDLQ?: boolean;
  queueOptions?: QueueOptions;
}
```

Consumer-specific options additionally include `maxRecoverRetries`, `backoffBase`, `maxBackoff`, and `recoveryJitter`.
